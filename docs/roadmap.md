## 全体方針: 取って・変換して・自己配信すれば表示できるライブラリ (2026-10-12)

**利用者のアイデアを精査して決めた。** 下の「このリポジトリは何か」(2026-09-26) の「未解決: 表示部分をライブラリにするか」への答え。

> **WebGIS を作りたい人が、データを取ってきて変換して自己配信すれば表示できる、というライブラリにする。**
> 使う人はどれか1つの地図ライブラリを使うので、**地図ライブラリごとに分け、共通部分を切り出す。**
> いまの Web サイトは**日本のカタログビジュアライザー** (ライブラリの使い方の見本も兼ねる)。

**分ける形 (案)。今回は方針を書くだけで、分ける作業はしない** (利用者の判断。10-18 に着手した。下の「ライブラリに分ける」):

| 部品 | 中身 | いまの在りか |
| --- | --- | --- |
| `core` | 地図に依らない: カタログを読む・DuckDB で引く・ジオコーディング・ライセンスを持ち回る | `packages/core` (10-18 に分けた) |
| `maplibre` | MapLibre で描く | `web/src/lib/tiles.ts`・`web/src/ui/` |
| `cesium` | Cesium で描く | `packages/cesium` (10-18 に分けた) |
| `deckgl`・`three`・`navara` | 下の「エンジン」 | `packages/{deckgl,three,navara}` (10-18 に分けた) |
| `pipeline` | 取る・変換する・STAC を書く (CLI) | `pipeline/`・`crates/remote-zip` |
| Web サイト | 日本のカタログビジュアライザー | `web/` の残り |

**気を付けること:**

1. **変換は Rust の CLI。ビルド済みにはしない** (2026-10-12、利用者。Rust を広めたい)。`cargo install` / `cargo run` で使ってもらう。
   ブラウザの中で変換する道 (下の「配らずに手元で変換」、WASM) は別の話として残る
2. **自己配信すると、配る責任が使う人に移る。** 基盤地図情報は測量法の複製の承認、PLATEAU は国交省の出典の書き方、
   Overture・OSM 由来は ODbL の継承。**ライセンスを持ち回る仕組み (STAC の `duck:attribution`・`duck:terms`、切り出した
   GeoParquet の KV) が、このライブラリのいちばんの売り**になる。README と出力で必ず伝える
3. **公開する API は約束になる。** npm に出すのは使い方が固まってから。まずは同じリポジトリの中でワークスペースに分ける
4. **リポジトリの名前**は `japan-geodata-catalog` に決めた (2026-10-14。下の「名前について」)

形式は自前で作らず、Portolan・stac-geoparquet に寄せる (下の「Portolan について」)。

### ライブラリに分ける (2026-10-18 に計画を決めた。利用者)

**作るのは、地図ライブラリの使い方の見本になる薄い部品。** 新しい GIS や枠組みは作らない。AI で独自のサイトが作りやすくなった今、
その質を支える見本という位置づけ (利用者)。コミュニティには「新しく作るより既存の基盤 (QGIS・STAC) で」という空気があり、
**指示ではないが判断材料として気にかける** (既存の道具でも開けるカタログにしておく、など)。

**手本は GeoLibre** (`.reference/github.com/opengeos/GeoLibre`、MIT)。MapLibre + DuckDB-WASM + deck.gl で、1つの層の一覧を4つのエンジンで描く。

- **エンジンとの口を1つの型に** (`packages/map/src/map-engine.ts` の `MapEngine`)。今の `CesiumRow`・`NavaraRow` を core の1つの型に寄せる
- **エンジンの名前ではなく「できること」の表で灰色を決める** (`layer-kind.ts` の、エンジンごとの描ける種類の表。漏れは型で落ちる)。
  今の一覧の定義にある `NOT_IN_SWAPPED`・`NOT_IN_NAVARA` (エンジンの名前ごとの灰色) を置き換える
- パッケージは **TypeScript のまま**読み込む (パッケージごとのビルドは無し)

| PR | やること | 状態 |
| --- | --- | --- |
| A `refactor/workspace-core` | ワークスペースの起点を直下へ (`pnpm-workspace.yaml`・lockfile・`.pnpmfile.cjs`)。`packages/core` を切り出す | 10-18 |
| B `refactor/engine-packages` | `packages/{deckgl,three,cesium,navara}`。**エンジンの実行時の資産を写す Vite のプラグイン**も部品に入れる。「できること」の表 | 10-18 |
| C `refactor/maplibre-package` | `packages/maplibre` (タイル・データの行の描き方・吹き出しの中身) | |
| D `refactor/pipeline-crate-name` | Rust のクレート名を `duck-geocoder` から付け直す | |

置き場所は **`web/` はそのまま、直下に `packages/*`** (`web/` を動かすと文書・CI のパスの直しが大きい)。名前は `@japan-geodata-catalog/*`
(npm には出さない)。**各 PR の前に本番ビルドの E2E を全件流す。**

**A でしたこと:**

- lockfile は `web/` から直下へ移し、中の起点の名前 (`.` → `web`) だけを直した。**解決した版は1つも変わっていない** (packages の部分の差分が0行)
- `core` は**アプリのビルドの設定 (`import.meta.env`) を読まない。** データと DuckDB-WASM の置き場所は、使う側が起動時に
  `configureData`・`configureDuckDb` で渡す (Web サイトは `VITE_DATA_BASE_URL` などを渡す)。ほかのアプリでも使えるように
- 言語の決め方 (`detectLang`・`lang`) は core が持ち、Web サイトはそれを使う (core の文言と画面の文言で言語がずれない)。
  core が使う文言 (注記・CityGML の種類の呼び名など) は core の `i18n.ts` に移した
- `igrc.ts` (SORA の表)・`detail.ts` (表示量の段。localStorage)・`view-params.ts` (URL) は Web サイトに残した。
  `tiles.ts` (MapLibre) は C、`engines/*`・`cesium-pmtiles.ts` は B で動かす
- 単体テストはワークスペースで流す (`pnpm -w run test:unit`。core 25件・Web サイト 12件)

**B でしたこと:**

- エンジンごとに `packages/<エンジン>` に分けた。中身は `src/engine.ts` (エンジン)・`src/draws.ts` (描ける種類の表)・`vite.ts` (実行時の資産を
  配る Vite のプラグイン)。依存 (cesium・three・deck.gl・Navara など) は Web サイトから各部品へ移した (解決した版は1つも変わっていない)
- **エンジンとの口は core の `engine.ts`**: 見え方 (`View`)・地図を入れ替えるエンジンの口 (`SwappedEngine`)・渡す行 (`EngineRow`。
  `CesiumRow`・`NavaraRow` を1つにした)・地形の選び方。Cesium・Navara は同じ口で、呼ぶ側はエンジンで分けずに `sync` を呼ぶ
- **灰色は「描ける種類の表」で決める** (core の `DrawKind`・`Draws`)。行の種類はデータの行・地図タイル・スタイル・ベクトルタイル・
  点だけのテーマ・3D Tiles の6つ。`NOT_IN_SWAPPED` などを消した。MapLibre に重ねるもの (deck.gl・Three.js) は、MapLibre の表と
  重ねるものの表の「どちらかが描ける」。表は `src/draws.ts` に置き、型だけに依るので、エンジン本体を読まずに引ける (起動を重くしない)。
  MapLibre の表は C で `packages/maplibre` へ移す (いまは `web/src/ui/engine-bar.ts`)
- 部品は**アプリのビルドの設定を読まない**。資産の置き場所は使う側が渡す (Cesium は `assetsUrl`、Three.js は `decodersUrl`)。
  Vite のプラグインに渡す置き場所と合わせる
- 開発サーバーでエンジンの資産を配るのは、R2 に似せた配り方 (Range など) ではなく、そのまま配るだけにした (`core/vite.ts` の `serveDirectory`)。
  `vite preview` ではビルドに写したものを配る (前は node_modules から配っていた)
- エンジンの部品の入口はどれも `engine.ts` なので、ビルドの JS の名前はパッケージの名前で出す (`cesium-*.js` など。`vite.config.ts`)
- `vite.ts` (Node の側) は型を確かめていない (`vite.config.ts` と同じ。前から)

**このあと (分けたあと):** スタイル (Portolan の `style` アセット) を core に足す。ジオコーダーの口。既存の道具 (QGIS・GeoLibre) で開けるかの確認と
Item の JSON (TOBE)。各パッケージの README (使い方の見本) は口が落ち着いてから。

### エンジン (2026-10-12)

MapLibre・MapLibre + deck.gl・MapLibre + Three.js・Cesium・Navara の5つ (2026-10-13 に全部「ざっと」入った)。

- Cesium・Navara は地図そのものを**入れ替える**。deck.gl (`MapboxOverlay`) と Three.js (3DTilesRendererJS など) は
  **MapLibre の上に重ねる** — 一覧・周辺検索・吹き出しは MapLibre のまま使える。バーでは別の項目に並べ、中身は「MapLibre ＋ 描き手」
- **deck.gl を先に。** DuckDB が返す Arrow をそのまま描ける (deck.gl-geoarrow。手元にクローンあり)。いまは WKB を自前で読んで
  GeoJSON にしているので、建物が多いときに効く見込み (**測っていない**)
- Three.js は MapLibre の上に 3D Tiles を重ねる道 (下の「Navara は立ち位置が違う」に既出)
- 「MapLibre 単体」はいまの MapLibre (バーの名前はそのまま)

**MapLibre + deck.gl をざっと入れた (2026-10-12、いまは `packages/deckgl`):**

- 建物 (DuckDB の行) と地形を deck.gl で描く。建物の MapLibre の層は透明にして残す (吹き出しは MapLibre が引き当てるので効く)。
  ジオメトリはいまは MapLibre と同じ GeoJSON。**座標の配列を直接渡す (binary)・GeoArrow で受けるのは次の段** (deck.gl-geoarrow は WKB を受けない)
- **deck.gl 9.4 の「同じ画面に重ねる」方式 (`interleaved`) は MapLibre 6 で動かない** — MapLibre の内部 (`map.transform`) を読み、
  6 ではそれが無い。**別の画面に重ねる**方式にした。代わりに地図の文字との前後関係は共有されない。MapLibre を上げても直らない (deck.gl 側の対応待ち)
- **地形は deck.gl の `TerrainLayer`** (利用者の指摘)。MapLibre の地形は deck.gl の間は外す (地形があると deck.gl がやはり内部を読んで落ちる)。
  表面には一覧のいちばん上の背景地図を貼る。読めるのは Terrarium の XYZ だけ (地理院の独自形式・COG なら Mapterhorn に替えてそう言う)。
  **別の画面なので、鉄道などほかの行は deck.gl の地形の下に隠れる**
- 建物は高さ 0 から押し出す。`TerrainExtension` (地形の高さを足す) を付けると**ヘッドレスでは建物が消えた**。GPU のあるブラウザで試すのが TOBE
- 色は出所ごとの塗りだけ (段の色分けは TOBE)
- pnpm 11 は公開から1日たたない版を入れない。deck.gl の部品 (`@loaders.gl/worker-utils` 4.5.4) がそれに当たり、pnpm が例外の設定
  (`pnpm-workspace.yaml` の `minimumReleaseAgeExclude`) を**黙って作った**。約束を緩めないよう消し、1日たってから入れ直した
- **`@deck.gl/geo-layers` (TerrainLayer) が脆弱性のある部品を3つ引き込み、コミット前の確認 (`scripts/audit.sh`) で止まった** (2026-10-13)。
  `fflate` は直った版 (0.7.5) に固定した。`image-size`・`sprintf-js` は Node で画像を圧縮する道具 (`texture-compressor`) の依存で、
  **ブラウザに配る中身には入らない** (本番ビルドの出力で確かめた) ので、理由と外せる条件を添えて受け入れた (`sprintf-js` は直った版がまだ無い)。
  設定は `pnpm-workspace.yaml` (10-18 からリポジトリの直下。pnpm 11 は `package.json` の `pnpm` を読まない)
  - **(10-16) 受け入れをやめ、依存から消した。** Dependabot は audit の受け入れを知らず、直せないまま失敗し続けた。
    texture-compressor は @loaders.gl/textures が import せず Node の別のプロセスとして動かすだけなので、`.pnpmfile.cjs` (10-18 からリポジトリの直下) で外した
    (任意の peer なので overrides の `-` は効かなかった)。配る中身 (dist の JS・WASM) は外す前と同じだった

**MapLibre + Three.js をざっと入れた (2026-10-13、いまは `packages/three`):**

- **先に MapLibre を 6.8 → 6.14 に上げた** (補助のライブラリ `maplibre-gl-three` が 6.12 以上を求める)。変更履歴に壊れる変更は無く
  (地形まわりの修正が多い)、全件の E2E で確かめた。6.13 で custom layer が地形に描ける口 (`renderToTerrainTile`) が増えている — deck.gl・Three.js の
  地形の問題に使えるかもしれない (TOBE)
- **`maplibre-gl-three` (MIT) + 3d-tiles-renderer (Apache-2.0) で 3D Tiles を MapLibre に重ねる。** 3D Tiles の行は MapLibre 単体・deck.gl では灰色、
  Three.js では描ける。ライブラリは地図が動くたびに見ている場所を原点に取り直すので、全国 (PLATEAU)・全世界 (Re:Earth) でも位置が合う
  (公式の例 (`maplibre-gl-js` の `f98ef79b4^:test/examples/add-3d-tiles-using-threejs.html`) はタイルセットの中心を原点にしていて、全国・全世界では合わない)
- **高さの基準を自動で合わせる:** ライブラリがジオイド (EGM96) の格子を読み、楕円体高 (3D Tiles) と海面 (MapLibre の地形) の差を引く。
  格子は PROJ の配信 (`cdn.proj.org`、パブリックドメイン) から読む — **自前で配るのは TOBE**。読めなければ補正なしで描き、地形の欄でそう言う
- Draco・KTX2 の読み手は jsDelivr ではなく three.js の同梱のものを自前で配る (`dist/three/`。ライセンスの文書も置く)
- custom layer なので**同じ画面に描く** — deck.gl のような「別の画面で地形の下に隠れる」問題は無い
- 見た目 (PLATEAU が地面に乗るか) は確かめていない (ヘッドレスで 3D Tiles を描かせると WSL が落ちた)。ボードの「確かめてほしいこと」
- **参考: Mini Tokyo 3D** (`.reference/github.com/nagix/mini-tokyo-3d`、MIT) は Mapbox GL v3 + deck.gl 8.9 の `Tile3DLayer` で PLATEAU を描き、
  Three.js は自前の層。MapLibre 6 ではないので deck.gl の件の答えにはならないが、deck.gl でも 3D Tiles を描ける道の実例

**PLATEAU の 3D Tiles が Three.js で抜ける件 (2026-10-14):**

- 利用者のスクリーンショットで、東京駅の周りの低い建物が抜け、間引かれた欠片が残った (高い建物は出る。Cesium・Navara では全部出る)。
  地形や DuckDB の建物を切っても変わらない。**描き手 (3d-tiles-renderer 0.5.3) のキャッシュの上限** (約430MB・8,000タイル) が疑わしい —
  README に「満杯になると粗いタイルを出したまま細かくするのを止める」とある。満杯になったらコンソールに出すようにした (確かめは利用者のブラウザ)
- **PLATEAU 配信サービスは LOD とテクスチャを URL で選べる** (`/datacatalog/3dtiles/<範囲>-<種類>-<LOD>[-interior][-<テクスチャ>]-<年>/tileset.json`。
  [API の説明](https://docs.plateauview.mlit.go.jp/api/rest/operations/datacatalog3dtilesspectilesetjson/))。カタログの `all-bldg-maxlod2-latest` は
  「LOD2 まで・テクスチャ優先」でいちばん重い組み合わせだった。**行の設定で LOD (1・2まで・3まで・4まで) とテクスチャ (あれば付ける・付けない) を選べる**ようにした
  (`packages/core/src/plateau-tiles.ts`。カタログはそのまま、URL の spec を組み替える)
- **利用者のブラウザで確かめた (10-15):** 既定の組み合わせではコンソールに `[three] tile cache full` が出た (**原因はキャッシュの上限で確定**)。
  「LOD2 まで・テクスチャ無し」と「LOD1」なら全部出る。あわせて出る `TilesRenderer: tiles versions at 1.1 or higher have limited support` は、
  PLATEAU が 3D Tiles 1.1 なので出る描き手の注意書き (描けてはいる)
- **LOD1 ではテクスチャを選ばせない。** 配信の一覧では LOD1 の建物はテクスチャが無いのにほとんど「テクスチャあり」で登録されていて
  (448件。「無し」は3件)、`lod1-notexture` は何も出なかった
- **Three.js では光を足し、テクスチャの無い面だけ光を受ける材質 (Lambert・面ごとの明るさ) に替える。** PLATEAU の glTF は光を受けない材質で、
  補助のライブラリは光を置かないので、テクスチャ無しは真っ白で形が読めなかった。太陽の向きは日本の真ん中で決め打ち (見た目は利用者が確かめる)
- **地図の既定は「LOD2 まで・テクスチャ無し」(10-15、利用者)。どのエンジンでも同じ** (行の設定はエンジンに依らない一覧の状態なので、
  エンジンごとに既定を変えると切り替えたときに表示が変わる)。カタログの URL は配信のいちばん詳しい形 (テクスチャ付き) のまま
- LOD1 と陰影は利用者のブラウザで確かめた (10-15)。コンソールに `THREE.GLTFLoader: Unknown extension "CESIUM_RTC"` が出ることがある。
  Three.js の道は補助のライブラリがこの拡張を登録しているので、Navara が同梱する glTF の読み手から出ているとみている (確かめていない)。
  どのエンジンでも建物の位置は合っているので、害は無い
- Navara の背景地図に最小のズームを渡していなかった。淡色地図 (ズーム2から) の 0/0/0.png を読みに行って 404 になっていた (利用者が見つけた。直した)
- 利用者が取ってくれた配信の一覧 (`/datacatalog/plateau-datasets` の `composite_tilesets`、`.reference/tmp/`) では、全国版に建物のほか
  橋梁・道路・植生・都市設備・地下街なども揃っている。**ほかの種類をカタログに足すのは TOBE**

**Navara をざっと入れた (2026-10-13、いまは `packages/navara`):**

- `@navaramap/three` 0.2.1 (MIT OR Apache-2.0) + `three-default-plugin`。Cesium と同じく**入れ替える側**で、同じページに載せて隠すときは入れ物を隠すだけ
  (変化があったときだけ描くので、隠れている間は描かない)。描くのは背景地図・3D Tiles・地形 (Re:Earth Terrain の quantized-mesh)。
  **ベクトルタイルとデータの行は灰色** (ベクトルタイルは URL テンプレートで受けるので PMTiles に中継が要る。Cesium の中継は Cesium の取得の口に差すもので使い回せない)
- 写真のような空 (`addDefaultPhotorealScene`) は使わず、光は ambient と太陽だけ。配る大きさは約29MB (WASM 4.6MB・大気のテクスチャ・
  Gaussian Splatting の部品 spark 5MB) だが、大気と spark は**使うときだけ読む**。初めて Navara を選んだときに読むのは JS 2.5MB と WASM
- **重ね順は足した順** (地形を先に)。並びや地形が変わったら地形から足し直す
- ズームと距離の行き来は Cesium と共用にした (いまは core の `zoom.ts`)。0.2.1 には MapLibre のズームと距離を行き来する関数が無い
- **画面の真ん中の地面は、描いた地表を拾わず、カメラの位置と向きから計算する** (視線と、地面の高さだけ膨らませた楕円体の交点)。
  `pickTerrainPosition` で拾うと、読み込みの途中の粗いタイルに当たって傾けた表示で約500mずれた (本番ビルドで。Cesium の約300mと同じ理由)
- **画角を明示する** (50°)。作った直後は `camera.fov` が読めず、仮の値で置いていてズームが 0.17 ずれた
- E2E は Navara に替えて同じ場所・灰色・3D Tiles を読みに行く・戻ると同じ場所、まで。**Navara から Cesium へ直接替えるところは E2E で流さない** —
  1ページに 3D のエンジンを2つ抱えると GPU の無いヘッドレスでは重く、本番ビルドで流した直後に WSL ごと落ちた (2026-10-13)。利用者のブラウザで確かめる
- 吹き出し・検索・データの行は TOBE (Cesium と同じ)

### ジオコーディング (2026-10-12)

`core` に「ジオコーダー」の口を作り、**独自 (DuckDB で自前の GeoParquet を引く)・住所の正規化 (Geolonia)・Nominatim** を並べる。
結果には必ず出典を添える。

- **Geolonia の community-geocoder は、このリポジトリと同じ「位置参照情報」が元。** 違いは住所の文字列の正規化
  (`@geolonia/normalize-japanese-addresses`、MIT。表記の揺れ・郡の省略・漢数字を吸収する)。CDN の `community-geocoder.js`
  (グローバル関数) より**正規化の部品を直接使う**。住所データの配信先は `config.japaneseAddressesApi` で差し替えられる
  (既定は Geolonia の配信) ので、**自己配信の方針と合う** (手元の `.reference/github.com/geolonia/`)
- **Nominatim の公開 API は利用方針が厳しい** ([利用方針](https://operations.osmfoundation.org/policies/nominatim/)、2026-10-12 に読んだ):
  毎秒1回まで (サイト全体で)・**入力しながらの候補表示は禁止**・結果はキャッシュ・ODbL の出典・大量や定期の問い合わせは不可。
  いまの検索欄は**入力のたびに (200ms 置いて) 引く**ので、Nominatim は**押したとき (Enter かボタン) だけ**の別の操作にする。
  ライブラリとしては**自前の Nominatim の URL を設定する形**にし、公開 API を既定にしない
- Nominatim の結果を GeoParquet に切り出すと ODbL がかかる (下の「気をつけること: ODbLの感染範囲」)

### OpenStreetMap の標準タイル (2026-10-12)

**カタログに載せるだけで、描かない** (利用者の判断)。[利用方針](https://operations.osmfoundation.org/policies/tiles/) は
条件付きで使える (出典を地図の上の目立つ所に・Referer・キャッシュを守る) が、**先読み・一括取得・オフラインを禁じ、保証が無く
予告なく止められる**。規約の厳しさを伝えるために載せた (`osm/osm-standard-tiles`、`duck:kind: reference`)。
タイルへのリンクは書かない (カタログの閲覧 (STAC Browser) が見本の地図として読みに行くため)。OSM のデータで背景地図を描くなら OpenFreeMap

## このリポジトリは何か (2026-09-26)

**名前を決めようとして、方針が言葉になっていないことに気づいた。** 先にここを書く。

> **置いてあるデータを動かさずに、必要な分だけ取って、その場で使えるようにする。**

### 変わらないもの

- **サーバーを持たない。** 静的ホスティングとオブジェクトストレージだけ
- **原典は配布元。** ここにあるのは変換した複製で、**正典のカタログを作るのではない**
- **必要な分だけ取る。** 全部落とさせない。範囲や列で絞って部分取得する

### いまの選択であって、主題ではないもの

**入れ替わりうる。** 名前にこれらを入れないのは、入れ替わったときに名前が古くなるから。

| | いまの選択 | なぜ主題ではないか |
| --- | --- | --- |
| 形式 | GeoParquet | **他のCNG (cloud-native geospatial) 技術も使う予定**。[COGPを測った](pipeline.md) (2026-09-27) |
| カタログ | STAC | **Portolanを使うならSTACはその一部**になる |
| 問い合わせ | DuckDB-WASM | **道具。** 別の技術が出れば移る |
| 表示 | MapLibre | 同上 |
| 対象 | 日本 | **売りではない。** 基本OGCに沿っており、海外のデータも入れられる |

### 題材であって、主題ではないもの

**ドローンの運航リスク評価。** 人口密度をSORAのiGRCで塗る機能があり、
道路・鉄道・障害物を集めているのもこの文脈だが、**主題ではない。**
このアプリでGCS (地上局) を作る想定は無いので、名前や説明に入れない。

### 未解決: 表示部分をライブラリにするか

**(2026-10-12) 決まった: ライブラリにする** (上の「全体方針」)。以下は決める前の記録。

**データをDLできたところで使えないと意味がない。** 表示までできているなら、
**そこを部品として切り出した方がよいのではないか**という問いが残っている。

いまの `web/` は「デモ」と「再利用できる部品」が混ざっている
(`web/src/main.ts` が3,500行)。切り出すなら境界をどこに置くかを決める必要がある。
**この立場が決まらないと名前も決まらない。**

### 名前について

**`japan-geodata-catalog` に決めた (2026-10-14、利用者)。** `duck-geocoder` は実態から外れていた (DuckDBは道具で、geocoderは機能の一つ)。

決めるまでに確かめたこと:

- **芯は「STAC と Portolan に沿って、日本に関するオープンデータを集めてみたカタログ。そのうえで可視化と問い合わせのために
  一部を加工して配信している」** (利用者の言い方)。STAC に沿うのは「中身の都合」ではない (CNG の界隈では STAC に沿わない
  カタログは微妙とされるほど)。カタログなら STAC に沿うのが当たり前なので、名前は `stac` より `catalog`
- 道具 (変換・地図の部品) とカタログを別の名前にする案は取り下げた。PLATEAU・国土数値情報・地域メッシュなど、**全体が日本のデータに最適化している**
- 「自己配信」は芯ではない (配信されているデータを使うだけもできる)。`lab` は public なリポジトリで名乗ると、注目されたあと変えにくい。
  `mirror` は加工しているので、リポジトリ全体の名前には合わない
- **ミラーとは、変換して置いている出所のサブカタログで名乗る** (ID に `-mirror`、説明に「非公式のミラー。原典は配布元」)。
  Portolan の registry で、1つの出所を写したカタログが ID と題名に mirror を付けている流儀 (`st-louis-open-data-mirror` など) に倣った。
  カタログ全体をミラーと呼ぶと、カタログの原典がどこかにあるように読めるので付けない。題名は画面の見出しに出るので付けない
- **個人の勉強用・実験用。registry には載せない** (日本のオープンデータへのアクセスが増えて、配布元の管理コストが上がるのは本意ではない)。
  名前は「場所 + 主題」の一般的な形 (registry でも `ireland-open-geodata`・`moldova-geodata` など)。ユーザー名が前に付くので、被っても構わない
- **GeoParquet の部分は本来は外に出すもの** (docs の比重が大きいのは意図ではなく副次的、利用者)。TOBE

**まだ古い名前のもの:** pipeline のクレート (`duck-geocoder`。ライブラリに分けるときに付け直す)、STAC の独自の項目の接頭辞 (`duck:`。
変えるとデータの上げ直しが要る)、R2 のバケット (URL に出ないので変えない)、`pyproject.toml` の名前、画面の状態を覚える localStorage の鍵。

**改名の費用は小さい**ことは確認済み。CIは
[deploy.yml](../.github/workflows/deploy.yml) が `github.event.repository.name` から
base pathを作るので直さなくてよく、R2のCORSもホスト単位なので影響しない。
直すのは文中の11か所と `stac.rs` の `CATALOG_ID` だけ。

## 測量法の承認申請 — 何がまとめて開くか

**方針は「国のデータを主に、Overtureは参考」。** これは撤回した「出所の格付け」
(全国を覆っていないものを外す) とは別物で、**OSM由来を根拠にしない**という
線引きの方。収録範囲の広さは理由にしない。

そのうえで詰まっているものは、ほぼすべて**同じ1つの手続きの先**にある。

| 欲しいもの | 承認が要るか |
| --- | --- |
| **鉄道 (N02)** | **不要。** 2020年以降は「適用する利用規約に基づく (オープンデータ)」 |
| **人口メッシュ・昼間人口** | 不要 (e-Stat、政府標準利用規約) |
| **N03 行政区域** | **要る** |
| **DID** | A16の原典に行政区域が入るので、N03に従う |
| **川 (基盤地図情報の水涯線)** | **要る** (基本測量成果) |

国土数値情報そのものは公共データ利用規約(PDL1.0)が既定で、**承認が要るのは
基本測量成果を背景図・原典に使っているものだけ**。個別ページの
「このデータの使用許諾条件」が正本なので、**データごとに読むこと。**
W05 河川はここで落ちた (非商用 + 承認番号 + 2009年度で更新停止)。

### 29条か30条かは決着した (2026-09-26) — **29条**

| | | 二次利用 |
| --- | --- | --- |
| **第29条 複製承認** | 測量成果を**そのまま複製**する | さらに複製・使用するとき**申請が要る場合がある** |
| **第30条 使用承認** | 測量成果を**使って別のものを作る** | **申請不要** |

**このリポジトリは29条。** 以前は「加工・編集して新たな成果品を作るので30条」と
書いていたが、理由が違った。**形式を変えるだけで、独自性のある内容を作っていない。**
[事例集](https://www.gsi.go.jp/LAW/2930-sample.html)にそのままの例がある。

> ベクトルデータ等（国土基本情報等）のデータ等を**地図データとして配布**する利用例です。
> → **第29条（複製）**

申請書の各欄の答え、成果品の一覧、残っている論点は
**[survey-application.md](survey-application.md)** にまとめた。

## UIの主役は geocoder (2026-09-20に決めた)

> 検索して飛んだ先で、**その場所に何があるか**が分かるのが理想。

**これは実験の主題と一致する。** STACの一番の効能は探索で、
「この場所にどのデータがあるか」は**bboxだけで、データ本体を読まずに答えられる**。

**済み:** データを**1データ1行のレイヤー一覧**にした (種別ごとに `<details>` を
積む形は、オープンデータを足すだけ縦に伸びて頭打ちが無かった)。
設定はパネルの中身と入れ替える。収録の無いものは「この範囲には無い」へ薄く移す。

**済み (2026-09-29):** 一覧を**カタログの階層そのもの**にした。以前は「建物」
「道路」のように使う側のまとまりで組んでいて、STACを使っていることが画面から
見えなかった (「PLATEAUやOvertureという分け方の方がカタログらしい。建物ベースで
出す便利機能はあってもよいが、このプロジェクトでやりたいことはそうではない」)。

- 出所ごとにサブカタログを挟み、それが見出しになる。Collectionが行
- 建物はPLATEAUとOvertureの2行で、同時に出せる (青と橙で塗り分け)
- ⚙ でCollectionの中身 (ファイル数・ライセンス・列) が出て、STACの文書を
  ページの中で開ける。`links` を押して親・子・Itemへ歩ける (2026-09-30)
- `description` を画面を見る人向けに書き直した。作る側の事情はコメントへ
- 「建物のある範囲へ移動」と「収録範囲を枠で示す」はやめた (2026-09-30)。
  どこにあるかは整備範囲のメッシュと一覧の「この範囲には無い」が示す

**済み (2026-09-30):** 使っている技術への謝辞を、データの出典と並べて出す。
**ライブラリとして使っているもの**と、**考え方・仕様だけ借りたもの** (STR・COGP・
PMTiles・Portolan・地域メッシュ・SORA) を分ける。後者はコードの依存に現れないので、
書かないと借りたことが見えない。PLATEAU GIS Converter の README の謝辞
(Planetiler の手法を参考にした旨) に倣った。

**残り:** Item (ファイル) の一覧までは出していない。PLATEAUは306件あり、
絞り込みのUIが要る。Overtureの建物は高さが無いものを3mで描くので、
両方出すとPLATEAUの高い建物の内側に隠れることが多い (重ね方は未検討)。

## 重要度・観点・沿線 (2026-10-01に方向を決めた)

**大事なのは、いろいろな用途に使える汎用の問い合わせを組めること。**
ドローンの「落ちてはいけない場所」「ポートに使えそうな場所」は思い付いた
用途の例にすぎず、それ専用の仕組みを作るのではない。

**済み:** 建物の重要度の段 (公共施設 / 商業・業務 / 住宅・その他)。
カタログに規則として載せる (詳細は pipeline.md)。**主な使い道は間引き** (引いた表示で
重要な段から出す)。寄ったときは段で絞ったり色分けしたりできる。
段の名前は当初「公共・要配慮 / 人が集まる」だったが、ドローン目線すぎたので建物の種類で言い直した。

**済み (2026-10-03):**

- **段で間引く。** 1ズーム引くごとに1段減らす (標準なら z14 で公共施設・商業・業務、
  z13 で公共施設だけ、それより引くと整備範囲)。東京駅 z13 は全部だと約30MB、
  公共施設だけなら約2MB。行は複製せず `lod` 列に段を入れて段ごとに行グループを切る
  (pipeline.md の「段で間引く」)
- **対象物の周辺検索 (◎)。** 起点は地図上の点・建物・線 (道路・鉄道・送電線・川。
  名前があれば同じ名前の区間をまとめる)・検索で選んだもの。50〜500m以内の建物 (段ごと)・
  駅・送電線・川・人口の概算を出す。**画面に出していないデータも数える**。
  **航路の設計そのものには踏み込まない** (UASLの文脈は業務に近すぎる)
  - (2026-10-10) **鉄道は路線全体にせず、押した地点の前後1.5kmだけを起点にする。** 東西線の沿線を
    丸ごと調べると R2 で1分半かかり、CI も落ちた。利用者の判断: 「沿線を丸ごと調べるのはハードすぎる。
    時間がかかるのは自然で、それに合わせて最適化しなくてよい。駅や駅と駅の間くらいでよい」。
    行グループより細かい範囲は並べ方を変えないと絞れない ([geoparquet-layout.md](geoparquet-layout.md))

**次:**

1. **観点 (問い合わせのひな形)。** 複数のCollectionにまたがる条件に名前を付けたもの。
   **条件はコードではなくデータ**で持ち、用途ごとに組み替えられるようにする
   (「落ちてはいけない場所」はその一例)。ポートの例は「駐車場など間借りできる場所」の
   想定で、公共施設を上げる程度でよい。周辺検索はその土台になる

**データは国土数値情報を優先する。** 新しいデータを足しやすい仕組みにしてあるので
できるだけ使う。候補: 学校 (P29)・医療機関 (P04)・福祉施設 (P14)・公共施設 (P02)・
都市公園 (P13)。**河川 (W05) は使えない** (上の表。非商用・承認番号付き・2009年度で停止)。
川は基盤地図情報の水涯線 (承認待ち) か、Overture。送電線は国土数値情報に
無いので Overture (元はOpenStreetMap、ODbL) を使う。**どちらも全国で入れた (2026-10-03)**:
送電線3.4万区間・川 (river と canal。小川・用水路は除く) 18.8万区間。

**済み (2026-10-03): 使う条件を一目で分かるように。** 出所ごとに「商用可か・出典表示・
加工の明記・継承 (同じライセンスで再配布)」をカタログ (`duck:terms`) に載せ、
⚙ のカードと出典のダイアログにバッジと規約へのリンクで出す。位置参照情報の出典は
規約が指定する書き方 (「大字・町丁目位置参照情報　国土交通省」など) に直した。

### 検索をどこまでやるか

**既存のジオコーダ・検索エンジンは使えない。サーバーが要るため**
(Nominatim・Photon・Pelias・Groonga。詳細は [data-sources.md](data-sources.md))。
このアプリに実行時のサーバーは無い。

**当てはまるのは「静的な索引を分割して、要る断片だけ取る」形** (Pagefindがそれ)。
**これは空間に対して既にやっていること**で、軸が場所か語かの違いしかない。
ただし**いまは作らない** — 駅名8,503種は `ILIKE` の走査で足りている。
**遅いと分かってから。**

**住所は自前で書かない。** `normalize-japanese-addresses` (MIT) が
v3でABRベースに作り直されている。ABRは位置参照情報の後継にあたるが、
**置き換えは別の判断**。いま動いているものを壊してまで急がない。

| | 状態 |
| --- | --- |
| 行政区域・地名 | 使用中 (位置参照情報) |
| **駅名・路線名** | **使用中** |
| PLATEAUの建物名 | **入れない。**51,170棟中326棟 (0.6%) しか名前が無い |
| 住所の精度 (ABR) | 未着手。急がない |
| 分割索引 | 未着手。**遅くなってから** |

**解決済み (2026-09-29):** レイヤー一覧の「この範囲には無い」判定は、以前は
Collectionのbbox (= **ファイルの和**) で見ていた。306都市に広げたので日本を
ほぼ覆う1つの箱になり、**収録の無い山間部でも一覧では「ある」と出ていた**。

いまは**整備範囲を持つ出所 (PLATEAU) だけ、表示範囲にセルが1つでもあるか**を
`LIMIT 1` で聞いて決める。箱の外なら聞かずに「無い」。飛騨の山中 (白山の東) で
「無い」に移ることをE2Eで見ている (直す前に落ちることを確かめた)。
転送量は増えていない — 描画と同じ行グループのbbox列を読むだけ。

**実験の主旨はここにある。** 配布元から落とすとPLATEAUのように巨大なzipになる。
変換して置いてあるのだから、使う側が楽になる道を用意したい。

| やりたいこと | いまの状態 | やるとしたら |
| --- | --- | --- |
| **配布元へたどり着く** | **済み。** STACの `rel: "via"` で出している (下記) | — |
| **必要な範囲だけ取る** | **済み (2026-10-03)。** ⚙ のカードの「この範囲を取得」。表示範囲を DuckDB-WASM の `COPY ... TO` で切り出す (30万件まで) | — |
| **GeoParquetで落とす** | **済み。** 同上。ファイル丸ごと (R2) と配布元へのリンクも並べる | GeoJSONも選べると一般には使いやすい |
| **CityGMLで落とす** | **済み。** PLATEAUだけ。表示範囲の3次メッシュで配信サービスのAPIを引き、メッシュ単位のGMLへの直リンクと、公式の `citygml/pack` でZIPにまとめる道の両方。**APIは押したときだけ呼ぶ** | — |
| **ライセンスを持ち回る** | **済み。** 切り出したGeoParquetのKVに出典・規約・元のファイルを書く | — |

| **いつ時点か分かる** | **済み。** `duck:vintage` をGeoParquetのKVに書き、出典欄とホバーに出す | ファイルごとに版が違うもの (PLATEAUは都市ごとに更新年度が違う) はまだ埋めていない |

### ズームで隠すのをやめた (2026-09-27)

以前は道路をズーム12未満、鉄道を10未満、建物を15未満で**出していなかった**。
転送量を抑えるためだったが、「**ズームしないとデータがあるか見えないのはUXが悪い**」。

隠さずに済ませる形は種別で違った。

| | やったこと | 引いた表示の転送量 |
| --- | --- | ---: |
| 道路・鉄道 | 路線ごとに統合・簡略化した行を**同じファイルに足す** (`lod` 列)。あわせて**等級でも絞る** (引いたら高速だけ) | 高速483KB / 鉄道329KB |
| 建物 | 建物そのものは出さず、**整備範囲を1kmのメッシュで出す** | 336KB (全国35,645セル・0.78MB) |

整備範囲の**濃淡は埋まり具合** (束ねた1kmセルのうち何割にデータがあるか) で付ける。
建物の数で濃くすると人口密集部が濃くなるだけなので使わない。メッシュコード・自治体・
建物数は**ホバーで読む**。自治体は1つに潰していない (約10%のセルが境界をまたぐ)。

**ファイルは増やしていない** (整備範囲の1つを除く)。PMTilesがタイルを1ファイルに
寄せているのと同じ理由で、解像度ごとに配信物を増やすと運用が破綻する。
測り方と落とし穴は [pipeline.md](pipeline.md) の「粗い段」にある。

**建物の段は、高さでは作らなかった。** 一度「60m以上」を作ったが**基準に根拠が無い** —
2Dなら面積、3Dなら高さで見たいものが違い、「引きで見たい施設」はそのどちらとも
別の概念。**いまは重要度の段 (用途と名前から) で間引く方向** (2026-10-01、上の節)。

**簡略化だけでは画面が読めない**ことも分かった。転送量は収まるが、全国の
都道府県道4,609本を描くと線で埋まり、ツールチップも拾うたびに移り変わる。
等級をズームで絞るのはそのため。

**COGPは採用していないが、乗り換えられる形にしてある** (物理配置が同じ)。
仕様の考え方が違う点と、道路網で測ったらCOGPの形では成り立たなかった数字も
同じ節に残した。

### 加工した旨と、何をしたか (2026-10-17)

利用者の指摘: PLATEAU は「加工したら明記」なのに、ⓘ のカードには使う条件のバッジだけで出典の文言が無かった。
**GeoParquet への変換は加工にあたる** (座標系を変え、属性を取り出し、並べ替えている)。

- **PDL1.0 の記載例は「「国土数値情報（○○データ）」（国土交通省）（URL）をもとに○○株式会社作成」**で、
  出典とは別に、加工した者の名前まで書く (国土数値情報の利用約款を 10-17 に読み直した)。以前は「をもとに作成」で、作った者が抜けていた
- **出典の1行 (`duck:attribution`) を「〜をもとに japan-geodata-catalog 作成」にした。** 地図の右下の ⓘ にはこれが出る
  (加工の表示を右下から消さない。見る人がいる場所で義務を果たす)。位置参照情報は規約の書き方を守って「(japan-geodata-catalog が加工)」
- **何をしたかは STAC の processing 拡張の `processing:lineage`** に書き、ⓘ のカードと「出典」に出す。加工した者は
  `providers` の `processor`・`host` (Portolan は producer と host が違えばミラーとみなす。サブカタログの `-mirror` と同じこと)
- 作った者の名前は**リポジトリの名前** (利用者以外も触りうるので、人の名前にしない。利用者)
- pipeline のテストが、配っている全データに何をしたかの説明があり、加工の表示が要るものは出典に作った者の名前があることを見る

### 配布元へのリンク (実装済み)

STACの **`rel: "via"`** は仕様上「**このEntityが作られる元になったメタデータ/データ**」
を指す関係 ([best-practices](https://github.com/radiantearth/stac-spec/blob/master/best-practices.md))。
**出典表示のリンク先とは役割が違う** — Overtureは出典がガイドページを指すのに対し、
配布元はデータのページになる。

2段で持っている。

| | 何を指すか | どこから来るか |
| --- | --- | --- |
| **Collection** | その出所のダウンロードページ | `Description::via` |
| **Item** | **そのファイル1つの配布元** | GeoParquetの `duck:via` (変換時に書く) |

**PLATEAUは都市ごとにzipのURLが違う**ので、変換時に `duck:via` へ書いている。
分からないとき (手元のzipから変換した場合など) は**書かない。推測で埋めない。**

`optimize_geoparquet` はKVメタデータを解釈せずそのまま引き継ぐので、
空間パッキングを掛けても配布元は残る。

## 外部の配信物をカタログに載せる (2026-10-03)

**公開されている cloud-native なファイルは、複製せずにカタログから指す。**
最初は地理院の最適化ベクトルタイル (PMTiles)。サブカタログ「国土地理院」の下に
テーマ (注記・道路・鉄道・建物・水部・地形・境界・構造物・送電線) ごとの行で出し、
行を開くと層ごとに入り切りできる。

- **背景地図ではなく、重ねるレイヤー。** 背景は1つしか選べないが、ベクトルタイルは重ねられる
- **入り切りはズームで戻さない。** 地理院地図Vectorはズームで出る層が変わると
  絞り込みが戻り、使いにくかった。描かれないズームでも行は残し「ズーム16から」と添える
- **一覧に絞り込み欄を付けた。** 出所の並びのまま、「送電」で Overture と地理院の
  送電線が並ぶ。行が増えても見通しを保つため
- SQL では引かない (表示用に簡略化されている。data-sources.md)

**描き方 (スタイル) は配布元のものを使わない** (2026-10-04)。権利の記載がデータにしか無い
(data-sources.md)。データだけを読み、形の種類 (カタログに載せた) から描く。

### 描き方 (スタイル) をどこで持つか (案, 2026-10-04)

**スタイルはデータではなく「データの見方」。** 権利も持ち主も別なので、データの
Collection とは分けて扱う。いまは UI のコードに入っている (`VECTOR_THEME_LOOKS`・
`LINE_STYLES`・建物の色) が、置き場所の候補は3段ある。

1. **UI が持つ (いま)。** 速く変えられるが、このアプリでしか使えない
2. **カタログに別の文書として置く。** `styles/<id>.json` (MapLibre の層の断片) を
   作り、Collection から**別のアセット (role `style`) かリンク**で指す。
   **スタイル自身のライセンスを持たせる** (うちの描き方ならリポジトリのライセンス)。
   データの規約 (`duck:terms`) とは別の欄にする — 混ぜると「データは使えるが描き方は不明」
   のような今回の状態を表せない。QGIS や stac-browser など**別の道具がうちの描き方を
   再利用できる**のが利点
3. **外部のスタイルは指すだけ。** 配布元の描き方は「参考 (権利の記載なし)」として
   リンクに留め、既定では使わない

標準の候補として STAC の render 拡張 (主にラスタ向け) と OGC API - Styles
(Collection ごとにスタイルを別の資源として持つ考え方) がある。**採る前に中身を読むこと。**
2 に進むなら、建物の段の色 (TIERS) のように**規則から生成**し、手書きの JSON を増やさない。

**済み (2026-10-04): 背景地図と地形もレイヤーにした** (QGIS と同じ形)。

- 地理院タイル (淡色・標準・航空写真・白地図) と Mapterhorn の標高を Collection にした。
  タイルは1ファイルではないので、STAC の **web-map-links 拡張のリンク**
  (`rel: "xyz"` / `"tilejson"`) で指す。地理院のベクトルタイルにも `rel: "pmtiles"` を足した
- 背景の淡色地図を外せば、地理院の注記と文字が二重に出る件も解ける

### 一覧を「データ」と「地図タイル」に分けた (2026-10-04)

最初は背景地図を出所の見出しの下の行にし、「後から入れたものが上」で重ねたが、
**重ね順が一覧から見えない**ので分かりにくかった (利用者の指摘)。QGIS の
「レイヤー」と「ブラウザ」の分け方に寄せた:

| 区分 | 中身 | 並び |
| --- | --- | --- |
| **データ** | SQL で引ける GeoParquet | 出所ごと (開け閉め) |
| **地図タイル** | ベクタータイルのテーマ・背景地図 | **出しているものを重ね順に** (上の行ほど上、↑↓ で入れ替え)。出していないものは「地図タイルを足す」に出所ごとにしまう |
| (地図タイルの中) **地形** | 標高を**1つ選ぶ** (Mapterhorn・Re:Earth・地理院) | 1行 |

データ (GeoParquet) は地図タイルより常に上に描く。

### 一覧には使うものだけを置き、カタログはダイアログで (2026-10-04)

上の形でも使いにくかった (利用者の指摘): 地図タイルは**外すと一覧から消え**、出し直すたびに
「地図タイルを足す」から探し直す。「足す」を開くと数十行が一度に開く。そこで:

| | 一覧 (左下) | カタログ (「＋ 追加」のダイアログ) |
| --- | --- | --- |
| 何を並べるか | **足したものだけ** | カタログの全部 (タブでデータ / 地図タイル、出所ごとの見出し) |
| 出す・隠す | チェック (**隠しても一覧に残る**) | — |
| 外す | ✕ | — |
| 重ね順 | 行の ⋮⋮ を掴んでドラッグ (キーボードは ⋮⋮ を選んで ↑↓)。上の行が上に重なる | 足すとき: 地図タイルはいちばん上、データは既定の重なりの位置 |
| 探す | — | 語で絞り込み。中の層だけに当たったら、その層だけを足せる |

- **データ同士の重ね順も変えられる**ようにした (建物と人口メッシュなど)。地図の層の並びは
  区分ごとの目印の層 (`anchor/tiles` `anchor/data`) の直下に積む (ui/layer-list.ts の `applyOrder`)
- 並べ替えは最初 ↑↓ のボタンだったが、**ドラッグにした** (レイヤーの並べ替えはこれが普通)。

## 配信形式: MLT (MapLibre Tiles)

**これは寄り道ではなく本題。** Portolanは「ベクタは **GeoParquet + PMTiles**」と
決めていて、**MLTはその後半を置き換える候補**だから。配信形式の評価そのものなので、
下の「切り出しの基準」1に真っ直ぐ当てはまる。

2026-01-23に1.0。列指向で、**大きなタイルで最大6倍の圧縮・デコード約3倍**。
**MapLibre GL JS は対応済み**で、スタイルに `encoding: "mlt"` と書くだけ。
ロードマップが**明示的にOvertureとGeoParquetに寄せている**。

**このリポジトリには計測装置がある。** E2Eが転送量を実測している
(`1.5 MB / 97.6 MB`) ので、**圧縮率の主張を自分のデータで確かめられる。**

経路とは別に**タイル化の工程が要る**。Planetilerの対応は近日段階。

### 行き先: バーで地図エンジンを切り替える (2026-10-12、利用者)

**上のバーで MapLibre・Cesium・Navara を切り替え、UI (一覧・カタログ・検索…) は同じ。そのエンジンで描けない項目は灰色にし、
描けるようにするのは TOBE。** ここまでの 3D のページ (別ページ) は「まず同じ場所を別のエンジンで開く」という**段取り**で、行き先ではなかった
(行き先がどこにも書かれていなかったので、別ページのまま積み増していた)。

**別ページにすると、行き来のたびに DuckDB-WASM の起動をやり直す。** Cesium・Navara でも DuckDB は使う (問い合わせはエンジンに依らず、
依るのは描く側だけ)。そこで先に「地図を DuckDB で待たせない」を入れ (下の「テストの時間」)、そのうえで1ページ (SPA) で入れ替えられるかを調べた。
利用者の記憶では「SPA でエンジンを入れ替えるのは大変」だった。

**調べた (2026-10-12、使い捨ての部品で。開発サーバー・Chromium):** 同じページで、MapLibre を隠して (`visibility: hidden`) Cesium を出し、
戻して `resize()`、を5往復した。

- **壊れたものは無かった。** MapLibre の層 (32)・ソース (23) は往復しても変わらず、戻って地図を動かすと建物の描き直し (DuckDB の問い合わせ) が走り、
  検索 (DuckDB) も使えた。エラー 0。画面も元どおり描かれた
- **主スレッドのメモリ**は Cesium を作った時点で 16MB → 60MB、その後の5往復は 60〜62MB で横ばい (GC のあと)。

- Navara も `ThreeView` に `init`・`dispose`・`addLayer`/`deleteLayerById`・カメラ・地形の高さを取る API があり、同じ形の口に収まりそう
- **本当に手間がかかるのは、エンジンの入れ替えではなく描く側。** `ui/layers/*`・`tiles.ts`・`hover.ts`・`layer-list.ts` に
  MapLibre の呼び出しが約100か所ある (`addLayer` 26・`getLayer` 17・`getSource` 15・`on` 13…)。ただしこれは別ページでも、
  Cesium で DuckDB のデータを描く (TOBE) ときに要る作業で、SPA だから増えるものではない。
  段階を踏めば、**口を作る前に** 入れ物だけ SPA にできる (Cesium では MapLibre に依らない行 = 背景地図・3D Tiles・ベクトルタイル・地形 だけを描き、
  データの行は灰色)

**判断の材料としては SPA (1ページ) で問題ない。** 起動は1回きりで、UI も本当に1つになる。利用者も SPA で進めると決めた。

### NASA と JAXA の標高 (2026-10-05 に調べた)

**どれも DTM (地面) ではなく DSM (地表。建物や木の上を測る) で、約30m。** 日本の中では、
いま使っている地理院の標高 (1m・5m・10m の DTM。Mapterhorn 経由) の方が細かく、地面を測っている。
足す意味は (1) 日本の外も覆う、(2) DSM − DTM で「地面より上にあるもの」(森・建物) の高さが概算できる、
(3) 外の STAC を参照するカタログの例になる。

| | AW3D30 (JAXA) | NASADEM (NASA) | ASTER GDEM v3 (NASA・経産省) |
| --- | --- | --- | --- |
| 中身 | ALOS の光学ステレオ。v4.1 (2024-04) | SRTM (2000年のレーダー) を作り直したもの | ASTER の光学ステレオ。2019 |
| 範囲 | 全球 | 北緯60°〜南緯56° | 北緯83°〜南緯83° |
| **入手** | **JAXA Earth API (STAC＋COG)。登録不要** | Earthdata (要ログイン)。Microsoft Planetary Computer (STAC＋COG。読むには匿名で取れる期限付きトークンが要る) | Earthdata (要ログイン)。COG あり |
| ブラウザから直接 | **読める** (Range・CORS `*`) | トークンの署名が要る | ログインが要る |
| 規約 | 改変・第三者への配布も可。**出所表示が要る** (例「提供：AW3D30 (JAXA)」)。**商用は事前に JAXA へ連絡が要る** | パブリックドメイン | 再利用・販売・再配布に制限なし。引用はお願い |

- **AW3D30 は JAXA Earth API が一番使いやすい。** STAC のカタログ
  (`https://data.earth.jaxa.jp/stac/cog/v1/catalog.json`) から
  `JAXA.EORC_ALOS.PRISM_AW3D30.v4.1_global` を辿ると、1°×1° の COG (東京付近で約10.7MB) が
  解像度の段 (0〜3) ごとに並ぶ。配信は Wasabi (S3互換) で、Range と CORS が開いている。
  日本域は EORC の配布ページでは v3.1 のままと書かれている (API の v4.1 にも東京のタイルはある。中身の版は未確認)
- 規約は JAXA 第一宇宙技術部門の「研究データ等の利用条件」(<https://earth.jaxa.jp/ja/data/policy/>)。
  うちの `duck:terms` で言うと「商用: 可 (事前に連絡)・出典: 要・改変: 可・継承: なし」
- NASA の2つは、手で落とす (Earthdata にログイン) か、Planetary Computer のトークンを使うことになる。
  パブリックドメインで条件は一番ゆるいが、**入手の手間とログインが要る**ので後回しにする

**進め方の案:**

1. **参照だけの Collection を足す** (`gsi-dem-source` と同じ形。配らない・上げない)。
   AW3D30 は JAXA の STAC Collection へのリンク (`via`) と規約を持たせる。
   NASADEM・ASTER GDEM も同じく出所と規約だけ。STAC Browser からそのまま辿れる
2. **AW3D30 を地図に出す** (必要なら)。COG を直接読むので R2 は使わない。MapLibre は COG を
   そのまま読めないので、COG を読む部品 (geotiff.js か、MapLibre の COG プロトコル) を足すことになる。
   陰影か、地理院の標高との差 (地面より上の高さ) を色で出す
3. NASA の2つを地図に出すのは、ログインやトークンの扱いが決まってから

**1 を入れた (2026-10-05):** `jaxa/jaxa-aw3d30.json`。利用者の狙いは DSM のまま
「**建物も木も無いところでは地面の高さの参考になる**」こと (DTM の代わりではない)。
公開元の STAC Collection は JSON の `rel: "alternate"` で指す (ビューアの `alternate` は HTML)。
JAXA の条件は「商用は事前に連絡」なので、`duck:terms` の `commercial` に
`allowed_with_notice` を足した (「可」と言い切らない)。参照だけの元データは足すダイアログに

**2 を入れた (2026-10-10): AW3D30 を地形に選べる。** 地形の欄の選択肢に AW3D30 が出る (日本の外も覆う)。

- **JAXA の COG を UI が直接読む** (R2 には置かない)。独自のプロトコル (`cogdem://`) で地図のタイルを頼まれたら、
  表示の細かさに見合う段と縮小版を選び、掛かる COG (1〜4個) から要る窓だけを読み、Web メルカトルに並べ直して
  Terrarium の画像にして返す (packages/core/src/cog-dem.ts)。地形も陰影も MapLibre の仕組みのまま

## JSON をまとめる (2026-10-07)

利用者の希望: 「JSON を何かしらの方法でまとめたい。できるだけ効率が落ちない方法で」。
英語版で文書が約2倍 (43 → 86) になるのもあって、読む側の往復を減らしたい。

**読むものが2種類あり、まとめ方を分けた。**

| 何を | どうした | 理由 |
| --- | --- | --- |
| **Item** (ファイル1つずつの href と bbox。761件) | **stac-geoparquet 1つ** (`items.parquet`)。Collection ごとに行グループを分ける | 使う Collection の分だけを Range で読める。JSON の15個 (約1.4MB) → 80KB |
| **Catalog と Collection** (起動時に全部読む) | 文書ごとの JSON は**残し**、アプリ用に**まとめ** (`collections.json` / `.en.json`) を足す | STAC (と STAC Browser) は1文書1ファイルが前提。アプリは起動時に1回読めば済む |

比べた案:

| 案 | 良いところ | 困るところ |
| --- | --- | --- |
| ItemCollection の JSON (前の形) | どの道具でも読める | PLATEAU に寄るだけで 607KB。Collection の数だけ往復 |
| **stac-geoparquet (選んだ)** | 小さい・必要な行グループだけ読む・仕様がある (STAC GeoParquet 1.1.0)。DuckDB がもう手元にある | **STAC Browser が Item の一覧を出せなくなる** (Collection までは辿れる)。読むのに DuckDB が要る |
| 全部を1つの JSON | 1回で済む | 使わない Item まで毎回読む (起動時に1.4MB) |
| zip などに束ねて Range で読む (PMTiles のように) | JSON のまま | 読む仕組みを自前で持つことになり、STAC の道具はどれも読めない |

**効率を落とさないために詰めたこと** (実測。開発サーバー):

- 最初の形では、起動時に items.parquet (137KB) のほとんど (110KB・7回) を読んでいた。
  DuckDB-WASM は **16KB のブロック単位**で取るので、行グループが1.6KBでもブロック1つになる
- フッターを削った (統計は `collection` と `bbox` だけ、辞書・ページの索引・arrow の型は書かない):
  ファイル 137KB → 80KB、フッター 44KB → 21KB
- **Item の多い Collection を前、少ないものを後ろ**に並べた。起動時に要る1〜2件の Collection が
  フッターと同じブロックに入る
- **DuckDB は文字列の統計を頭の部分でしか比べない。** `WHERE collection = 'plateau-buildings-coverage'`
  でも `plateau-buildings` の行グループを確かめに行く。フッターの統計から行番号の範囲を求め、
  `file_row_number` で絞った
- 結果: **起動時は 47KB・3回** (まとめ 88KB の JSON 1回とは別)。PLATEAU に寄って読み足すのは
  **16KB** (前は 607KB の JSON)。起動時の JSON の読み込みは 3段・43回 → 1回
- 起動時だけを見ると、以前の小さな ItemCollection 4つ (各数KB) より読む量は多い。
  往復が減ったことと、建物を出したときの差 (約590KB) の方が大きいと判断した

**仕様から外したところ:** stac-geoparquet はファイルのメタデータに Collection の JSON を入れることを
勧めているが、入れない (フッターを読むたびに32個ぶんがついてくる。Collection は JSON にある)。

**STAC Browser のパッチ** (`rel: items` の相対パスの解決) は、`rel: items` が無くなったので
効く場面が無くなった。上流が直したら外す方針のまま残す。

## R2 の読み込み1回の重さ (2026-10-08、未決)

建物の間引き (10-03) を R2 の実データで初めて流したら、デプロイの E2E が落ちた。
**R2 の公開URL (r2.dev) は読み込み1回ごとに約0.45秒待たされる** (転送は約2MB/秒)。
DuckDB-WASM は1回ずつ順に読むので、往復の回数がそのまま待ち時間になる。

- 建物は並べ方を直して、寄った表示を 10-03 より前と同じかそれ以下にした
  (pipeline.md の「建物の並べ方」)
- **残る重いところ:** 引いた表示の間引き (z13.x で約45秒。20近いファイルを開く往復が大半) と、
  逆ジオコーディング (約30回で13〜16秒)

## 配らずに変換する・カタログだけ持つ (2026-10-05、利用者の構想)

**(2026-10-10) 優先度を下げた** (利用者の判断)。先に AW3D30 (COG)・3D の別モード・測ったことの記事に取りかかる。

PLATEAU GIS Converter のように、**データを配らずに、利用者の手元で変換する仕組み**を用意する。
あるいは**カタログだけ**持つ。そうすれば、測量法などで配れないデータも扱える余地がある。

**賛成。このリポジトリの主題 (STAC 配布形式の実験) にも合う。** 扱い方を3段に分けて考える:

| 段 | うちがすること | 権利の重さ | 例 |
| --- | --- | --- | --- |
| 配る | 変換して R2 に置く | 規約が再配布を認めるものだけ | PLATEAU・Overture・国土数値情報 (いま) |
| **手元で変換する** | 変換の仕組み (WASM) と手順だけ配る。データは利用者が自分で取り、ブラウザの中で変換し、外に出さない | 複製・頒布するのは利用者自身。うちは配らない | 基盤地図情報 (標高・水涯線)、N03 |
| **カタログだけ** | 出所・条件・入手方法・変換の手順を STAC に書く | ほぼ無い | `gsi-dem-source`・AW3D30 (いま) |

- **測量法の29条 (複製承認) が掛かるのは**、測量に使うため・刊行するため・不特定多数が
  受け取れる状態に置くために複製するとき。手元で変換して自分で見るだけなら、
  うちは複製も頒布もしない。ただし**利用者がその結果を配ったり測量に使ったりすれば、
  利用者に承認が要る**。仕組みの側で条件をはっきり出す。解釈は地理院に確かめてから進める
- **自動で取りに行けるかは出所次第。** PLATEAU の配信 API は CORS が開いていて
  ブラウザから直接取れる (調べ済み)。基盤地図情報はログインが要り、手で落としたファイルを
  ブラウザに渡す形になる
- **ブラウザの制約:** WASM のメモリ (4GB まで)、大きなファイルの扱い (OPFS に置く)。
  基盤地図情報は JPGIS の GML なので読む部品が要る。パイプラインの Rust (と nusamai) を
  WASM にできるかが鍵
- カタログには「変換すれば使える」ことと手順を書く。STAC には処理を書く拡張
  (processing) があるので、独自の項目より先に見る

### 3D Tiles のテクスチャと 3DGS (構想)

**全部を配るのは厳しいので、要る範囲だけをその場で WASM で変換して見せる。** 賛成。
上の「手元で変換する」の 3D 版になる。

- **テクスチャ付きの建物:** PLATEAU のメッシュ単位の CityGML (配信 API から取れる。CORS 可) を
  WASM で 3D Tiles か glTF にする。nusamai (PLATEAU GIS Converter の中身) は既に
  テクスチャ付きの 3D Tiles を書き出せるので、WASM にできれば一番近い。
  PLATEAU が既に 3D Tiles で配っている都市は、変換せずカタログから指せばよい (Re:Earth Buildings と同じ形)
- **3DGS (Gaussian Splatting):** 写真から学習して作るものなので、CityGML や点群から
  変換では作れない。**既にある splat を指して描く**のが現実的。描く側は Cesium が 3D Tiles の中の
  splat に対応を進めていて、Three.js にも描く部品がある (どれも版と対応状況は確かめてから)
- **地図エンジン:** 安牌は Cesium (3D Tiles・地形・テクスチャが一番こなれていて、PLATEAU VIEW も
  Cesium)。MapLibre＋Three.js は今の一覧や描き方と同じ地図に重ねられるが、地形やカメラを
  合わせる手間が大きい。Navara は新しく (0.1)、地理院の標高をそのまま読めるが、まだ変わりやすい
- **進め方の案:** 変換の部分 (WASM → 3D Tiles/glTF) は地図エンジンに依らないので、そこを先に作る。
  確かめは Cesium で行う (Cesium で正しく出れば、データは正しい)。そのあと MapLibre＋Three.js で
  同じ地図に重ねるかを決める。Navara は版が上がるのを待つ

## 調べたこと (2026-10-04)

### GeoArrow

DuckDB-WASM は、ジオメトリの列を**そのまま返すと既に GeoArrow** (`geoarrow.wkb`、CRS 付き) で返す。
東京駅付近の建物 2.8万棟で測った (読み込み済み、ネットワークを除く):

| 経路 | 問い合わせ | JS 側 | 計 |
| --- | ---: | ---: | ---: |
| いま: `ST_AsGeoJSON` → `JSON.parse` | 245 ms | 72 ms | 317 ms |
| GeoArrow (WKB) のまま返す | 160 ms | (WKB を読む。未実装) | — |
| (参考) MapLibre の `setData` | | 430 ms | |

GeoArrow にすると問い合わせ側で約 1/3 減るが、**大きいのはネットワークと MapLibre の `setData`**
(GeoJSON を地図の Worker でタイルに切り直す)。`setData` を避けるには GeoJSON を経由しない描き方
(deck.gl の GeoArrow 層など) が要る。geoarrow-js は WKB を読まない (読むのは geoarrow-rs の WASM) ので、
WKB を読む小さな関数を自前で書いた。

**入れた (2026-10-05):** `lib/wkb.ts` で WKB を直接読む。同じ 2.8万棟で、JS 側は
`JSON.parse` 約43ms → WKB 約6〜14ms (Node で測った)。問い合わせと合わせて約317ms → 約170ms。
表示範囲の問い合わせ・周辺検索・ハイライト・行政区域の形を全部置き換えた。

### STAC Browser

Radiant Earth の STAC Browser (Vue のページ) は、**地図ではなくページで**カタログを辿る標準の画面。
このカタログのリンクにもう対応している: `rel: "3d-tiles"` は Cesium Sandcastle で開く、
GeoParquet のアセットは geoparquet.info で開く、PMTiles は Protomaps のビューアで開く。

| 使い方 | 手間 | 要るもの |
| --- | --- | --- |
| 公開されているもの (radiantearth.github.io/stac-browser) に URL を渡す | 無し | R2 の CORS にそのオリジンを足す |
| ビルドして GitHub Pages の `/browser/` に置く | デプロイに1工程 | `catalogUrl`・`pathPrefix`・`historyMode: hash` を設定。同じオリジンなので CORS はそのまま |

**手元で見た (2026-10-05):** STAC Browser 5.1.0 を `/tmp` で動かし、開発サーバーのカタログを
読ませた (`SB_catalogUrl`・`SB_historyMode=hash`)。サブカタログ8つ、Collection の説明・範囲の地図・
Item の一覧 (PLATEAU 306件)・`duck:*` の項目 (使う条件など) がそのまま出た。

**置いた (2026-10-05):** 利用者が見て、置くと決めた。名前は `/catalog/` にした
(`/browser/` は何を見るものか分からない。カタログを見る画面なのでそのまま名乗る)。
デプロイで版 (v5.1.0) を固定して取ってきて、[stac-browser/](../stac-browser/) の設定とパッチでビルドする。
ⓘ のカードから、その Collection を開ける。

- **STAC Browser の不具合にパッチを当てた:** カタログから辿って Collection を開くと、
  項目一覧 (`rel: items` の相対パス) を Collection ではなくページの URL 基準で解決し、404 になる
  (先に読んで控えてある Collection を使うときに、基準の URL がまだ空)。直接開くと起きない。
  上流に報告できる形 (1か所・6行) にしてある。直ったらパッチを外す
- 出る警告のうち `unload is not allowed`・vue-i18n の Legacy API は STAC Browser 自身のもの
  (後者は開発サーバーだけで、本番ビルドでは出ない)
- ソースマップを除いて約18MB (除かないと51MB)。ビルドは約40秒
- **権利 (2026-10-05 に確かめた):** STAC Browser は ISC。使う・変える・配るのは自由 (商用も) で、
  条件は「複製に著作権表示と許諾表示を含める」だけ。束ねている依存 (185件) も MIT・Apache-2.0・BSD・ISC
  などで、コピーレフトは無い。**ビルドが表示を落としていた**ので、`/catalog/LICENSE` と
  `THIRD-PARTY-LICENSES.md` (Vite の `build.license`) を一緒に置くようにした。
  背景地図は OSM の公式タイルで、出典は出ている (アクセスの少ないサイトなら OSM の利用方針の範囲)
- **同じ穴がアプリ本体にもあった。** MapLibre・DuckDB-WASM の JS などの表示を `THIRD-PARTY-LICENSES.md` に、
  写して配っている DuckDB の本体と拡張の表示を `duckdb/LICENSES.md` に置いた。spatial 拡張は
  **GEOS (LGPL-2.1) を静的に持つ**ので、その本文とソースの在りかも。変えずに配り、ソースは誰でも
  手に入るので、表示を置けば足りる。**CDN から読む形に戻す必要は無い** (外のドメインに頼らない
  ために自前で配っている判断はそのまま)
- **宿題: Item に名前と時点が無い。** 一覧が `plateau_bldg_01100` のような ID で並び、
  「No time given」と出る。`datetime: null` に `start_datetime`/`end_datetime` が無いのは
  STAC としても正しくない。都市名と年度は PLATEAU の配信カタログにあるので、

- 見て分かったカタログの不具合: 3D Tiles と参照だけの元データに `duck:tile_size: 0` を書いていた

## 気をつけること: ODbLの感染範囲

**再頒布そのものは4つとも認められている** ([README](../README.md) のライセンス節)。
問題になりうるのは**ODbLの同一ライセンス条項がどこまで及ぶか**。

いまは **Overture由来のファイルと他を別ファイルとして配っている**ので、
PLATEAUや国勢調査のものにODbLは掛からない。

**結合したファイルを作ると話が変わる。** 例えば「Overtureの行政区域で人口メッシュを
集計したファイル」を作ると、それが Derivative Database (ODbLが及ぶ) なのか
Collective Database (及ばない) なのかという判断が要る。

**軸2の「必要な範囲だけ取る」でも同じことが起きる。** 切り出したものが
複数の出所をまたぐなら、出力に**どの出所が混ざっているか**が分かる形にしないと、
受け取った側がライセンスを判断できない。

## 切り出しの基準

「別リポジトリに分けるか」という問いへの答え。**いまは分けない。**

1. **配信形式が増えるだけなら、同じカタログ。** STACは形式を問わない。
   Portolanが「ベクタはGeoParquet + PMTiles、ラスタはCOG、点群はCOPC」を
   1つの仕様にしているのはそのため。**COPCを足すのに別リポジトリは要らない**
2. **実行時に外部APIを叩くものは、データ層に入れない。** プレビュー側の機能
3. **分かれ目はデータの種類ではなく「配る」と「使う」の間。**
   いま `web/` が両方やっている。判断ロジック (SORAの計算、航路生成) が
   育ったら、そこが切れ目になる

## Portolan について

[Portolan](https://www.portolan-sdi.org/) は同じ構成 (オブジェクトストレージに
静的ファイル + STAC + GeoParquet) を仕様にしたもの。**まだ準拠していない。**

> Every catalog and collection carries `catalog.json` or `collection.json` for machines,
> plus `README.md` and `AGENTS.md` for people and agents.

Portolanが求める `README.md` / `AGENTS.md` は**配信するデータの側**に置くもので、
このリポジトリのAGENTS.mdとは別物。`data/output/` 側にはまだ無い。

準拠を名乗るのはv1.0が見えてから。v0.2.0で破壊的変更が予告されている。

- **点群の生データを配ること。** TB級。持つなら派生物にする
- **SDSP/UASLの文脈を深追いすること。** どんなデータが求められているかの
  参考にはするが、目的には掲げない
